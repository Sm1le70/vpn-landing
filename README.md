# Лендинг + личный кабинет (Remnawave 3.3 + Platega + Resend)

Node.js 24, Express, SQLite (встроенный `node:sqlite`). Внешних сервисов, кроме панели, Platega и Resend, нет.

## Что умеет

- **Лендинг** (`/`): возможности, шаги подключения, тарифы с ценами, FAQ, контакты. Всё рендерится на сервере, поэтому банк увидит тарифы и контакты даже без JavaScript.
- **Документы:** `/terms` (пользовательское соглашение), `/privacy` (политика конфиденциальности), `/contacts` (поддержка). Ссылки на них есть в шапке, подвале и форме оплаты.
- **Кодовое слово** для проверки Platega выводится в подвале каждой страницы. После регистрации кассы очистите его в админке (**Настройки**).
- **Личный кабинет** (`/cabinet`): вход по email и одноразовому коду, статус подписки, ссылка, QR-код, число устройств, продление, история платежей.
- **Оплата:** разовые платежи через Platega (`/v2/transaction/process`), способ оплаты клиент выбирает на форме Platega. Автосписаний нет.
- **Выдача доступа:** после подтверждённой оплаты создаётся пользователь в Remnawave, а если он уже есть — срок продлевается от текущей даты окончания. Ссылка на подписку приходит на почту.
- **Пробный период:** один раз на email. Дополнительно — один раз на устройство (HWID): если устройство уже подключалось к другой пробной подписке, новая пробная подписка отключается.
- **Админка** по секретному пути: пользователи и подписки, платежи и возвраты, обращения в поддержку, статистика, тарифы, приложения, настройки, сотрудники с ролями, журнал действий. Подробнее — в разделе [Админка](#админка).
- **Обращения:** письма на адрес поддержки принимаются через Resend Inbound и собираются в переписки в админке; отвечать клиентам можно прямо оттуда. Подробнее — в разделе [Обращения](#обращения).
- **Поддержка в Telegram:** бот заводит для каждого клиента тему в закрытой группе сотрудников; ответ в теме уходит клиенту. Подробнее — в разделе [Поддержка в Telegram](#поддержка-в-telegram).

## Быстрый тестовый запуск (демо, без ключей)

Нужен только Node.js 22.13+ (проверка: `node -v`).

```bash
npm install
npm run demo
```

Откройте http://localhost:3000. В демо-режиме Platega, Remnawave, Resend и Telegram заменены заглушками: настоящих платежей нет, панель не нужна, `.env` не требуется.

Что попробовать:
1. **Лендинг:** главная, тарифы, `/terms`, `/privacy`, `/contacts`.
2. **Вход:** «Личный кабинет» → введите любой email → **код входа появится в консоли**, где запущен `npm run demo` (строка `Код входа: 123456`).
3. **Оплата:** выберите тариф → поставьте галочку → «Оплатить» → откроется **тестовая платёжная страница** → «Оплатить». Вас вернёт в кабинет с активной подпиской, ссылкой и QR-кодом. Кнопка «Отменить» показывает сценарий неудачной оплаты.
4. **Продление:** оплатите ещё раз — срок увеличится.
5. **Пробный период:** войдите под другим email → «Активировать пробный период».
6. **Админка:** http://localhost:3000/admin-demo/ — логин `admin` / пароль `admin` (или `support` / `support` для роли поддержки). В демо эти учётки входят без 2FA; настоящие админы всегда проходят 2FA.
7. **Обращения:** в админке **Обращения → Сымитировать письмо** (или в соседнем терминале `npm run demo:mail -- --from client@example.com --subject "Вопрос" --text "Текст"`). Заглушка Resend «принимает» письмо и отправляет сайту подписанный вебхук — как в настоящей работе. Ответьте из карточки обращения: ответ появится в консоли. Затем сымитируйте ещё одно письмо с галочкой «Ответ клиента на последний ответ поддержки» — оно попадёт в ту же переписку. В демо-письме специально есть скрипт и внешняя картинка: в HTML-версии они не срабатывают.

8. **Telegram:** в соседнем терминале `npm run demo:tg -- --text "Не подключается"` — это сообщение клиента боту. В консоли демо появятся создание темы, карточка клиента, копия сообщения и автоответ. Ответ сотрудника в теме: `npm run demo:tg -- --topic 2 --text "Обновите приложение"`. Закрыть тему: `--close 2`. Привязка аккаунта: в кабинете нажмите «Написать в Telegram», скопируйте токен из адреса открывшейся вкладки (`...?start=ТОКЕН`) и выполните `npm run demo:tg -- --start ТОКЕН`.

Порт по умолчанию 3000. Другой можно задать через `DEMO_PORT`, например в PowerShell: `$env:DEMO_PORT=3300; npm run demo`.

Письма в демо не отправляются, их текст (и заголовки ответов поддержки) выводится в консоль. Остановить: `Ctrl+C`. Начать заново: удалите `data/demo.db`. Заглушка панели хранит пользователей в памяти, поэтому после перезапуска демо старые подписки «пропадут» — это нормально.

Запуск с реальными ключами локально: `cp .env.example .env`, заполните его и выполните `npm start`. Callback от Platega на `localhost` не дойдёт, но статус оплаты подтянется, когда вы вернётесь в кабинет.

## Установка на сервер

Команды ниже рассчитаны на Ubuntu/Debian и пользователя с `sudo`. Репозиторий: `https://github.com/Sm1le70/vpn-landing`. Замените `example.com` на ваш домен (A-запись домена должна указывать на IP сервера).

### 1. Docker и Git

Пропустите, если Docker уже стоит (например, рядом с панелью Remnawave):

```bash
sudo apt update && sudo apt install -y git curl
curl -fsSL https://get.docker.com | sudo sh
docker compose version    # проверка
```

### 2. Скачать проект

```bash
sudo mkdir -p /opt/vpn-landing && sudo chown $USER: /opt/vpn-landing
git clone https://github.com/Sm1le70/vpn-landing.git /opt/vpn-landing
cd /opt/vpn-landing
```

Если репозиторий **приватный**, нужен доступ только на чтение. Проще всего — deploy key:

```bash
ssh-keygen -t ed25519 -f ~/.ssh/vpn_landing_deploy -N ""
cat ~/.ssh/vpn_landing_deploy.pub
# GitHub → репозиторий → Settings → Deploy keys → Add deploy key (без права записи)
GIT_SSH_COMMAND="ssh -i ~/.ssh/vpn_landing_deploy" \
  git clone git@github.com:Sm1le70/vpn-landing.git /opt/vpn-landing
cd /opt/vpn-landing
git config core.sshCommand "ssh -i ~/.ssh/vpn_landing_deploy"   # чтобы работал git pull
```

### 3. Настроить `.env`

```bash
cp .env.example .env
# Секреты генерируются сразу в .env:
sed -i "s|^APP_SECRET=.*|APP_SECRET=$(openssl rand -hex 32)|" .env
sed -i "s|^ADMIN_PATH=.*|ADMIN_PATH=/panel-$(openssl rand -hex 6)|" .env
nano .env
```

В `nano` заполните как минимум:
- `SITE_URL=https://example.com`;
- `REMNAWAVE_URL`, `REMNAWAVE_TOKEN`, `REMNAWAVE_SQUADS`, `REMNAWAVE_WEBHOOK_SECRET`;
- `PLATEGA_MERCHANT_ID`, `PLATEGA_SECRET`;
- `RESEND_API_KEY`, `MAIL_FROM`.

Название, контакты и дату документов можно задать здесь же или потом в админке. Путь к админке посмотрите командой `grep ADMIN_PATH .env` и сохраните его — он нужен для входа.

`.env` и папка `data/` в Git не попадают (см. `.gitignore`), поэтому ключи и база не утекут при `git push`.

### 4. Запустить

```bash
mkdir -p data && sudo chown 1000:1000 data     # контейнер работает от пользователя node (uid 1000)
docker compose up -d --build
docker compose logs vpn-landing                # ссылка для создания первого админа
```

Приложение слушает `127.0.0.1:3000` — снаружи оно недоступно, пока перед ним не встанет reverse-proxy.

### 5. HTTPS через Caddy

Platega принимает callback только на HTTPS с валидным сертификатом. Если на сервере ещё нет reverse-proxy:

```bash
sudo apt install -y caddy
sudo tee /etc/caddy/Caddyfile >/dev/null <<'EOF'
example.com {
    reverse_proxy 127.0.0.1:3000
}
EOF
sudo systemctl reload caddy
```

Caddy сам получит сертификат Let's Encrypt (порты 80 и 443 должны быть открыты). Если на сервере уже работает Caddy или nginx панели Remnawave, добавьте в его конфиг отдельный блок для домена лендинга с тем же `reverse_proxy 127.0.0.1:3000`.

**Панель Remnawave на этом же сервере.** Сайт может обращаться к ней по внутренней сети Docker, без выхода в интернет. Для этого:
1. в `docker-compose.yml` раскомментируйте блоки `networks` (сеть панели обычно называется `remnawave-network`, проверьте командой `docker network ls`);
2. укажите в `.env` `REMNAWAVE_URL=http://remnawave:3000`;
3. выполните `docker compose up -d`.

### 6. Проверить

- `https://example.com` — лендинг, тарифы, `/terms`, `/privacy`, `/contacts`.
- `https://example.com/<ADMIN_PATH>/` — админка: создайте первого администратора по ссылке из логов (шаг 4).
- В кабинете Platega укажите callback `https://example.com/webhooks/platega`, в `.env` панели — вебхук `https://example.com/webhooks/remnawave` (подробности ниже, в разделе «Настройка»).
- Сделайте тестовую оплату минимального тарифа.

### Обновление

```bash
cd /opt/vpn-landing
git pull
docker compose up -d --build
docker compose logs -f --tail=50 vpn-landing    # убедиться, что запустилось (Ctrl+C — выйти из логов)
```

База данных лежит в `data/` вне контейнера и при обновлении сохраняется, новые колонки добавляются автоматически.

### Резервная копия

Всё состояние — это `data/app.db` (пользователи, заказы, админы, настройки) и `.env`:

```bash
cd /opt/vpn-landing
mkdir -p backups
docker compose exec vpn-landing node -e "new (require('node:sqlite').DatabaseSync)('/app/data/app.db').exec(\"VACUUM INTO '/app/data/backup.db'\")"
mv data/backup.db backups/app-$(date +%F).db && cp .env backups/env-$(date +%F)
```

Ежедневный бэкап по cron (хранятся 14 последних копий):

```bash
( crontab -l 2>/dev/null; echo "0 4 * * * cd /opt/vpn-landing && docker compose exec -T vpn-landing node -e \"new (require('node:sqlite').DatabaseSync)('/app/data/app.db').exec(\\\"VACUUM INTO '/app/data/backup.db'\\\")\" && mv data/backup.db backups/app-\$(date +\\%F).db && ls -1t backups/app-*.db | tail -n +15 | xargs -r rm" ) | crontab -
```

Восстановление: `docker compose down`, положить копию как `data/app.db`, `docker compose up -d`.

### Полезные команды

```bash
docker compose ps                                  # статус
docker compose logs -f vpn-landing                 # логи в реальном времени
docker compose restart                             # перезапуск
docker compose exec vpn-landing npm run admin:list # администраторы
```

Без Docker: `git clone …`, `cp .env.example .env`, затем `npm ci --omit=dev && npm start` (нужен Node.js ≥ 22.13; для автозапуска — systemd или pm2).

## Админка

### Первый запуск
1. Задайте в `.env` секретный путь, например `ADMIN_PATH=/panel-x7k2` (латиница, цифры, `_` и `-`, от 6 символов). По другим адресам админки не видно: там обычный 404.
2. Запустите сайт и посмотрите лог:
   ```bash
   docker compose logs vpn-landing
   ```
   Там будет одноразовая ссылка вида `https://example.com/panel-x7k2/#/setup/…` (действует 1 час, при каждом перезапуске выдаётся новая, пока админ не создан).
3. Откройте ссылку, задайте логин и пароль, отсканируйте QR-код в приложении-аутентификаторе (Google Authenticator, Aegis, 1Password…) и сохраните 10 резервных кодов.

Остальных сотрудников приглашайте из админки (**Администраторы → Пригласить**): вы получите одноразовую ссылку на 24 часа.

### Восстановление доступа из консоли
Если все админы потеряли доступ (телефон с 2FA и резервные коды):
```bash
docker compose exec vpn-landing npm run admin:list
docker compose exec vpn-landing npm run admin:reset -- --login ivan         # новая ссылка: пароль + 2FA; отключённая учётка включится после сброса
docker compose exec vpn-landing npm run admin:create -- --login olga --role support
```
Команды печатают одноразовую ссылку. Без Docker — те же `npm run …` в папке проекта.

### Роли
| | Поддержка | Администратор |
|---|:-:|:-:|
| Пользователи и платежи (просмотр, поиск) | ✓ | ✓ |
| Сброс устройств, перевыпуск и повторная отправка ссылки | ✓ | ✓ |
| Обращения: чтение, ответы, смена статуса | ✓ | ✓ |
| Продление подписки | только существующей, до 7 дней за раз | без ограничений, в т.ч. сокращение |
| Выдача доступа без оплаты, отключение/включение, сброс пробного периода | — | ✓ |
| Удаление подписки и аккаунта | — | ✓ |
| Возвраты через Platega, сверка заказов | — | ✓ |
| Сводка, CSV, тарифы, приложения, настройки, сотрудники | — | ✓ |
| Журнал | только свои действия | все |

Каждое действие с клиентом требует причину и пишется в журнал (кто, когда, что было до и после). Для большинства действий есть галочка «Уведомить клиента по email».

### Выдача подписки вручную
Подписку можно назначить, не дожидаясь оплаты:
- **Пользователи → Выдать доступ** — по email. Аккаунта ещё нет? Он создастся. Срок берётся из выбранного тарифа либо задаётся вручную («Свой срок»).
- В карточке клиента — **Продлить / сократить**: дни добавляются к текущему сроку, а если подписки нет, она создаётся (только роль «Администратор»; поддержка продлевает лишь существующую подписку).

Пользователь в панели Remnawave создаётся с теми же сквадами и лимитом устройств, что и при обычной оплате. Клиент входит в кабинет по своему email и видит ссылку и QR-код.

### Удаление
В карточке клиента, только для роли «Администратор»:
- **Удалить подписку** — пользователь удаляется из панели Remnawave, ссылка перестаёт работать. Аккаунт на сайте и история платежей остаются: клиент может войти и оформить подписку заново.
- **Удалить аккаунт** — то же самое плюс обезличивание: email заменяется на `deleted-<id>@deleted.invalid`, сессии, коды входа, отметки об устройствах и переписка с поддержкой (обращения с этим email) удаляются, email скрывается и в журнале (остаётся вид `an***@mail.ru`). Требуется ввести email клиента для подтверждения. Подходит для запросов на удаление персональных данных (политика конфиденциальности, п. 5.3).

Записи о платежах в обоих случаях сохраняются — они нужны для отчётности и разбора споров с банком; email в них тоже обезличивается. После удаления аккаунта прежний email снова свободен: клиент может зарегистрироваться заново.

### Обращения
Раздел доступен обеим ролям. Письма, пришедшие на любой адрес домена приёма (например, `support@one.pro-stor.org`, а также ответы клиентов на письма с `no-reply@`), собираются в переписки.

- **Список:** фильтры «Открытые», «Непрочитанные» и по статусам со счётчиками, поиск по email и теме. Число непрочитанных видно рядом с пунктом меню.
- **Статусы:** «Новое» — первое письмо, ответа ещё не было; «Ждёт ответа» — клиент написал после нашего ответа; «Отвечено» — последний ответ наш; «Закрыто». Письмо клиента в закрытую переписку открывает её снова.
- **Карточка:** переписка по порядку, ссылка на карточку пользователя (если email зарегистрирован на сайте), вложения, смена статуса, форма ответа. В карточке пользователя есть блок с его обращениями.
- **Ответ** уходит с адреса `SUPPORT_FROM`, с темой `Re: <тема>` и заголовками `In-Reply-To`/`References`, поэтому у клиента он попадает в ту же цепочку. Внизу цитируется последнее сообщение клиента (время — по Москве). После ответа статус — «Отвечено» (или «Закрыто», если отмечена галочка). Ответы и смены статуса пишутся в журнал.
- **Привязка писем:** сначала по `In-Reply-To`/`References` к сохранённым Message-ID, иначе по email отправителя и теме без `Re:`/`Fwd:` среди незакрытых переписок, иначе создаётся новая.

Безопасность:
- По умолчанию показывается текстовая версия письма. HTML открывается кнопкой в `iframe` с `sandbox` (без скриптов и доступа к админке), а сервер отдаёт его с CSP `default-src 'none'` — внешние картинки, шрифты и пиксели отслеживания не загружаются. Санитайзер не нужен: изоляцию обеспечивает браузер, новых зависимостей нет.
- Вложения не хранятся на сервере: при скачивании сайт запрашивает у Resend свежую ссылку и отдаёт файл как `application/octet-stream` с `Content-Disposition: attachment` (до 25 МБ; больше — скачайте в панели Resend).
- Автоответы и рассылки (`Auto-Submitted`, `Precedence: bulk/junk/list/auto_reply`, `X-Autoreply`, `List-Id`), отчёты о недоставке и письма с наших собственных адресов обращений не создают — так ответы не зацикливаются.
- Сохраняется до 200 тыс. символов текста и 1 млн символов HTML; если письмо больше, в карточке будет пометка.

### Возвраты
В платеже: **Возврат** → админка проверяет возможность возврата в Platega и показывает, сколько USDT спишется с баланса → вы выбираете, что сделать с подпиской (снять дни этого заказа, отключить, не трогать) → подтверждаете. Если Platega отвечает, что нужна ручная обработка, заказ получает статус «Возврат в обработке» — свяжитесь с поддержкой Platega.

### Безопасность
- Пароли хранятся как scrypt-хэши, 2FA (TOTP) обязательна, резервные коды одноразовые.
- 5 неверных попыток входа — блокировка логина и IP на 15 минут.
- Сессия админа — 12 часов, cookie только для пути админки (`SameSite=Strict`).
- Отключённый клиент не может оплатить подписку из кабинета, пока его не включат.

## Настройка

### Тарифы, приложения, контакты, пробный период
Редактируются в админке (**Тарифы**, **Приложения**, **Настройки**) и сразу применяются на сайте. Значения из `.env` (`BRAND_NAME`, `SUPPORT_EMAIL`, `TRIAL_DAYS` и т.д.) и файлы `config/plans.json`, `config/apps.json` используются только как начальные — после сохранения в админке действуют значения из базы. Тексты проверяются на недопустимые для банка формулировки при сохранении.

### Remnawave
1. **Настройки → API Tokens**: создайте токен и запишите его в `REMNAWAVE_TOKEN`.
2. **Internal Squads**: скопируйте UUID нужных сквадов в `REMNAWAVE_SQUADS` (через запятую).
3. Для проверки устройств на пробном периоде:
   - в панели должна быть включена функция **HWID Device Limit**;
   - в `.env` панели задайте `WEBHOOK_ENABLED=true`, `WEBHOOK_URL=https://example.com/webhooks/remnawave` и `WEBHOOK_SECRET_HEADER=<секрет>`;
   - тот же секрет запишите в `REMNAWAVE_WEBHOOK_SECRET`.

   Без вебхука устройства пробных подписок проверяются опросом раз в 5 минут.

### Platega
1. Запишите `PLATEGA_MERCHANT_ID` и `PLATEGA_SECRET`.
2. В кабинете Platega: **Настройки → Callback URLs** → `https://example.com/webhooks/platega`.

Callback проверяется по заголовкам `X-MerchantId`/`X-Secret`, после чего статус и сумма перепроверяются через `GET /transaction/{id}`. Если callback не дошёл, фоновая задача раз в минуту сверяет неоплаченные заказы младше 2 часов. Статус заказа также проверяется, когда клиент возвращается в кабинет.

### Resend
Подтвердите домен в Resend и заполните `RESEND_API_KEY` и `MAIL_FROM`. Без ключа письма (включая коды входа) пишутся в лог — это удобно для локальной проверки.

### Resend Inbound (обращения в поддержку)
Пример — для домена `one.pro-stor.org` с DNS в Dynadot. Точные значения записей копируйте из панели Resend: они зависят от региона аккаунта.

**1. Домен в Resend.** Resend → **Domains → Add Domain** → `one.pro-stor.org`. Resend покажет записи для отправки. В Dynadot: **My Domains → pro-stor.org → DNS Settings**, раздел записей поддоменов (Subdomain Records):

| Поддомен | Тип | Значение |
|---|---|---|
| `resend._domainkey.one` | TXT | DKIM-ключ из Resend (`p=...`) |
| `send.one` | MX | адрес из Resend, приоритет из Resend |
| `send.one` | TXT | SPF из Resend (`v=spf1 include:... ~all`) |
| `_dmarc.one` (необязательно) | TXT | `v=DMARC1; p=none;` |

Дождитесь статуса **Verified** (обычно минуты, иногда до нескольких часов).

**2. Приём почты.** На странице домена включите **Receiving** — Resend покажет ещё одну MX-запись. В Dynadot добавьте:

| Поддомен | Тип | Значение |
|---|---|---|
| `one` | MX | адрес приёма из Resend, приоритет из Resend |

У `one` не должно быть других MX-записей с меньшим числом приоритета, иначе почта уйдёт не в Resend. A-запись сайта для `one` остаётся — MX ей не мешает. В Resend нажмите **I've added the record** и дождитесь статуса Verified. Проверка из консоли: `nslookup -type=mx one.pro-stor.org`.

**3. Вебхук.** Resend → **Webhooks → Add Webhook**:
- URL: `https://one.pro-stor.org/webhooks/resend-inbound`
- событие: `email.received`

Откройте созданный вебхук и скопируйте **Signing Secret** (`whsec_...`) в `RESEND_INBOUND_WEBHOOK_SECRET`. Caddy настраивать не нужно: маршрут обслуживает то же приложение.

**4. Ключ API.** Для чтения входящих писем и вложений ключ должен иметь права **Full access** (ключ «Sending access» подходит только для отправки). Если текущий ключ ограниченный — создайте новый в **API Keys** и замените `RESEND_API_KEY`.

**5. `.env` и перезапуск:**
```
RESEND_INBOUND_WEBHOOK_SECRET=whsec_...
SUPPORT_EMAIL=support@one.pro-stor.org
SUPPORT_FROM=Поддержка <support@one.pro-stor.org>
MAIL_FROM=MyVPN <no-reply@one.pro-stor.org>
# SUPPORT_NOTIFY_EMAIL=you@example.com   # короткое уведомление о новых обращениях
```
```bash
docker compose up -d --build
```
Если email поддержки уже сохранён в админке (**Настройки**), поменяйте его там — значение из `.env` используется только до первого сохранения.

**6. Проверка.** Напишите на `support@one.pro-stor.org` с личной почты — через несколько секунд письмо появится в **Обращениях**. Ответьте из админки, затем ответьте на этот ответ из почты: письмо должно попасть в ту же переписку. Если письма нет — посмотрите в Resend **Emails → Receiving** (дошло ли письмо до Resend) и **Webhooks → ваш вебхук** (статус доставки), а также `docker compose logs vpn-landing | grep support`.

Как это работает: вебхук `email.received` содержит только метаданные, поэтому сайт проверяет подпись (Svix, окно 5 минут), ставит письмо в очередь по `email_id` (повторная доставка не создаёт дубль) и забирает текст и заголовки через `GET /emails/receiving/{id}`. Если API Resend не отвечает, попытки повторяются около 33 часов (1 мин, 5 мин, 30 мин, 2 ч, 6 ч, 12 ч, 12 ч); если письмо так и не получено, обращение создаётся из метаданных с пометкой. Message-ID отправленного ответа сайт получает через `GET /emails/{id}` — по нему привязывается следующее письмо клиента.

### Поддержка в Telegram
Бот копирует сообщения клиента в его тему в закрытой группе сотрудников, а сообщения сотрудников из темы — клиенту. Отвечать можно с телефона, в группе может быть сколько угодно сотрудников. Клиент видит только бота.

**1. Бот.** В [@BotFather](https://t.me/BotFather): `/newbot` → имя и юзернейм → скопируйте токен. Там же можно задать описание и аватар (`/setdescription`, `/setuserpic`).

**2. Группа.** Создайте группу в Telegram, в настройках включите **Темы** (Topics). Добавьте бота и сделайте его администратором с правом **Управление темами**. Остальные права не нужны.

**3. `.env` и перезапуск:**
```
TELEGRAM_BOT_TOKEN=123456:ABC...
```
```bash
docker compose up -d --build
```
Напишите в группе `/chat_id` — бот ответит ID группы (только пока он не указан). Темы должны быть уже включены: при их включении Telegram меняет ID группы. Добавьте ID и перезапустите ещё раз:
```
TELEGRAM_SUPPORT_CHAT_ID=-100...
```
При запуске сайт сам регистрирует вебхук `<SITE_URL>/webhooks/telegram`, например `https://example.com/webhooks/telegram` (нужен https в `SITE_URL`) и проверяет, что в группе включены темы и у бота есть права. Проблемы видны в `docker compose logs vpn-landing | grep telegram`. Сообщения из других групп бот игнорирует; если у группы поддержки сменился ID, в логе будет новый ID.

**4. Проверка.** Напишите боту с личного аккаунта — в группе появится тема с вашим именем, карточкой и сообщением. Ответьте в теме обычным сообщением — оно придёт вам от бота, а на сообщении сотрудника появится реакция 👌 (доставлено).

**Как работать:**
- Каждый клиент — отдельная тема. Первым сообщением в ней бот публикует карточку: имя, @username, Telegram ID и, если аккаунт привязан, email, срок подписки и ссылку на пользователя в админке.
- Ответ — обычное сообщение в теме: текст, фото, файлы, голосовые. «Ответить» на конкретное сообщение работает в обе стороны.
- Сообщения, начинающиеся с `//`, — внутренние заметки: клиенту они не уходят.
- Вопрос решён — закройте тему (меню темы → **Закрыть**). Когда клиент напишет снова, бот откроет её сам и отправит автоответ.
- Команды в теме: `/info` — обновить карточку, `/ban` и `/unban` — перестать или снова начать пересылать сообщения клиента (спам).
- Если сообщение не доставлено (например, клиент остановил бота), бот напишет об этом в теме.
- Если тему удалили, при следующем сообщении клиента бот создаст новую.

**Привязка к аккаунту.** В личном кабинете есть кнопка **Написать в Telegram**: она открывает бота по одноразовой ссылке (действует 30 минут), и бот привязывает Telegram к аккаунту — в названии темы и в карточке появляется email. Если клиент пишет боту напрямую, аккаунт не привязан — попросите email. Привязанный Telegram виден в карточке пользователя в админке. При удалении аккаунта привязка снимается, email убирается из названия темы, сама тема остаётся.

**Ссылки на сайте.** Когда бот запущен, ссылки Telegram в подвале и на странице «Контакты» ведут на бота, а не на юзернейм из настроек.

**Ограничения Telegram:** бот не может написать клиенту первым (только после «Start»); в одну группу бот отправляет не больше ~20 сообщений в минуту — при наплыве сообщения придут с задержкой, но не потеряются. Клиент может отправить не больше 20 сообщений в минуту, дальше бот просит подождать. Правки уже отправленных сообщений не пересылаются.

Как это работает: вебхук проверяет секрет в заголовке `X-Telegram-Bot-Api-Secret-Token` (выводится из `APP_SECRET` и токена), ставит обновление в очередь по `update_id` (повторная доставка не создаёт дубль) и обрабатывает очередь по порядку. Если Telegram не отвечает, попытки повторяются около 2 часов (10 с, 30 с, 1 мин, 5 мин, 15 мин, 30 мин, 1 ч), при этом сообщения одного клиента не обгоняют друг друга. Переписку хранит Telegram; сайт хранит только соответствие «клиент — тема» и номера сообщений для ответов.

## Требования Platega и банка

- Цены, документы и контакты поддержки (email и Telegram-юзернейм, не группа) доступны с каждой страницы.
- На сайте нет данных ИП/ООО/ИНН.
- Тексты не содержат формулировок про обход ограничений. Проверка: `npm run check-wording`. Запускайте её после каждой правки текстов, включая FAQ и письма.
- Перед отправкой на проверку заполните `SITE_URL` в `.env`, а название, контакты поддержки и дату документов — в админке (**Настройки**) или в `.env` до первого сохранения.

## Задел под Telegram-бота

Пользователь в БД идентифицируется по email, а в Remnawave у него есть поле `telegramId`. Привязка Telegram к аккаунту уже есть (таблица `tg_clients`, одноразовая ссылка из кабинета) — её можно использовать и для бота продаж. Логику выдачи (`applyPaidOrder`, `startTrial`) можно переиспользовать без изменений.
